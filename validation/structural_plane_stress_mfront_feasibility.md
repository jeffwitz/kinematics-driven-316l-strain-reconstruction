# `StructuralPlaneStress3D`: TFEL/MFront 5.1 feasibility

## Scope and inspected installation

This report is the first feasibility gate for a generic structural plane-stress
closure. It does not modify TFEL, MFront behaviours, or the Python adapter.

The inspected installation is:

```text
MFront/TFEL: 5.1.0
TFEL git hash: deee4cd
prefix: /home/jeff/.local
library: /home/jeff/.local/lib/libTFELMFront.so.5.1.0
headers: /home/jeff/.local/include/MFront
```

The executable needs `LD_LIBRARY_PATH=/home/jeff/.local/lib` in this checkout.
The installation provides public headers and documentation, but not a complete
TFEL source checkout; conclusions below are therefore based on the installed
5.1 public API, exported symbols and installed DSL documentation.

## Executive verdict

| Question | Result |
|---|---|
| Register a first-level brick from an external library? | **The loader works, but the installed build cannot load a normal external brick implementation.** |
| Compose several bricks in one behaviour? | **Yes, at the parser/description level.** |
| Derive/decorate the concrete `StandardElasticity` implementation externally? | **Not demonstrated; no public concrete header is installed.** |
| Inject code into residual, Jacobian, tangent and auxiliary-state stages? | **Partly.** Named code blocks can be created/replaced/appended, but the API is string/code-block based rather than a typed transformation API. |
| Recover a generic `K(x)` and `dK/dx` from every compatible law? | **No public contract found.** |
| Safe V1 genericity claim | **Only behaviours implementing an explicit additional adapter contract**, unless a prototype proves a narrower `StandardElasticity` code-block contract. |

The promising route is therefore an external parser brick plus an explicit
small-strain implicit behaviour contract. The unsafe assumption is that a brick
can discover and rewrite the residual generated by `StandardElasticity` for an
arbitrary existing behaviour without the law exposing named elastic-residual
blocks.

## 1. External brick registration

The installed header `MFront/InitDSLs.hxx` explicitly documents the
`MFRONT_ADDITIONAL_LIBRARIES` environment variable for loading user libraries.
The installed binary exports `mfront::BehaviourBrickFactory` and its
`registerAbstractBehaviourBrick` overloads.

The registration surface is:

```cpp
using constructor = std::shared_ptr<AbstractBehaviourBrick> (*) (
    AbstractBehaviourDSL&, BehaviourDescription&);

BehaviourBrickFactory::getFactory()
  .registerAbstractBehaviourBrick(name, behaviour_type, integration_scheme,
                                  constructor);
```

The loader itself works, but the minimal external probe in
`validation/mfront/structural_plane_stress_brick_probe.cxx` fails when MFront
loads the module. The installed `libTFELMFront.so.5.1.0` does not export the
out-of-line implementation symbols needed by a normal derived brick, including
`BehaviourBrickBase::treatKeyword` and the `AbstractBehaviourBrick` destructor.
The loader reports an undefined symbol before the registered brick can be
listed. The relevant symbols are local in the installed shared library even
though the factory registration methods are exported.

Therefore, **an external first-level brick is not usable with this exact
installation** without one of the following changes:

1. rebuilding TFEL/MFront with the required brick base symbols exported;
2. adding an upstream/plugin-ABI change that makes the brick API loadable;
3. compiling the brick into the MFront library itself.

This is a concrete ABI/visibility blocker, not a missing include or a problem
with the proposed plane-stress equations. It also means that
`MFRONT_ADDITIONAL_LIBRARIES` proves the library-loading mechanism, but does
not by itself prove external Behaviour Brick support.

## 2. What a brick can actually control

`AbstractBehaviourBrick` exposes a lifecycle suitable for parser extensions:

- `initialize` receives brick parameters and data;
- `treatKeyword` can parse brick-specific options;
- `getDescription` declares supported hypotheses and managed variables/code
  blocks;
- `completeVariableDeclaration` runs after variable declarations;
- `endTreatment` runs at the end of input treatment.

`BehaviourBrickBase` supplies common variable/property helpers. The public
`BehaviourDescription` additionally exposes `appendToIncludes`,
`appendToMembers`, `appendToPrivateCode`, `addAuxiliaryStateVariable`,
`setCode`, `getCode` and code-block names. `BehaviourData` names the relevant
blocks, including `Integrator`, `ComputeTangentOperator`,
`UpdateAuxiliaryStateVariables`, `InitializeJacobian` and
`AdditionalConvergenceChecks`.

This means a brick can add variables and insert or replace generated C++ code
at `AT_BEGINNING`, `BODY` or `AT_END` positions. It does **not** expose a typed
residual/Jacobian AST, a callback specifically “before `@Integrator`”, or a
typed hook to replace selected rows of the implicit system after another brick
has generated them. Code-block composition is possible, but its correctness
depends on named blocks, insertion order and generated symbols.

`@TangentOperator` is evaluated after integration variables, stresses and
auxiliary variables have been updated. `@UpdateAuxiliaryStateVariables` is a
post-integration hook. Neither one, by itself, is a mechanism for changing the
local Newton system before convergence.

## 3. `StandardElasticity` and the proposed `feel` oracle

The installed `StandardElasticity` documentation confirms that the brick is
built on the `Hooke` stress potential and that the implicit integrator exposes
the residual through `fzeros` and its Jacobian through `jacobian`. The implicit
DSL documentation also confirms that `deto` is the total-strain increment and
that integration-variable residuals use the current increment estimates.

The useful algebraic observation remains valid for a compatible law:

$$
f_{el}(x)=K(x)-\Delta\varepsilon
\quad\Longrightarrow\quad
K(x)=f_{el}(x)+\Delta\varepsilon.
$$

However, no installed public API exposes “the elastic residual block” as a
typed object, nor its derivative as a law-independent `dK/dx` object. A brick
could inject C++ that refers to the generated `fzeros` and `jacobian` symbols,
but it must know their row layout and distinguish the elastic rows from all
constitutive rows. That is not a generic contract for arbitrary `Implicit`
behaviours.

Consequently, the `feel` route is a strong prototype hypothesis, not yet a
generic implementation foundation. It should first be tested on a deliberately
small behaviour whose residual blocks are explicitly named or registered by an
adapter contract.

## 4. Multiple bricks and `@Import`

The parser supports multiple registered bricks through the DSL's internal brick
collection, and `@Import` includes external MFront files sequentially through
the current directory, `--search-path`/`--include`, or
`MFRONT_INCLUDE_PATH`. These mechanisms support:

- sharing constitutive fragments with `@Import`;
- composing existing bricks in one behaviour;
- loading an external brick implementation through
  `MFRONT_ADDITIONAL_LIBRARIES`.

They do not automatically make two behaviours share one generated physical
implementation, and they do not provide a late wrapper that can safely alter
an already-generated behaviour's Newton equations. SRIX deduplication through
`@Import` is therefore a separate, controlled refactor and should not be
coupled to the first plugin feasibility test.

## 5. Structural rotation and tangent implications

The proposed structural closure is compatible with the existing convention:
the host supplies an unrotated structural/global strain, while the closure
uses a per-point structural-to-material rotation to evaluate the three free
tractions in the structural frame. The brick must own neither host substepping
nor composite-FD policy.

The one-step brick would need to replace the three transverse kinematic rows by
the three structural traction rows and expose the corresponding consistent
tangent. The installed API can insert code into the named Jacobian and tangent
blocks, but it does not provide a generic row-replacement operation. A first
prototype must therefore make the row convention explicit and test it against
the existing raw 3D Schur oracle before any claim of generality.

## 6. Recommended implementation order

1. Keep the failed external probe as a regression artifact and decide whether
   exporting the brick base classes is acceptable upstream.
2. Until that decision, build a J2/`StandardElasticity` prototype with an explicit, documented
   elastic-residual/Jacobian contract. Do not claim arbitrary-law support yet.
3. Compare its one-step response and tangent with native plane stress and raw
   3D condensation.
4. Apply the same contract to SRIX and Méric without writing law-specific GPS
   equations.
5. Only after those tests succeed, evaluate whether the contract can be
   promoted to a reusable `StructuralPlaneStress3D` brick.

No TFEL fork is justified by the current evidence. The first engineering choice
is whether to request/export a small upstream ABI surface for bricks. If that is
not accepted, the next fallback is a small local extension of the implicit DSL
or an explicit adapter contract, not a silent claim of arbitrary MFront
compatibility.

## Final genericity level at this gate

```text
[ ] arbitrary MFront behaviour
[ ] arbitrary Implicit small-strain behaviour
[ ] arbitrary StandardElasticity-compatible Implicit behaviour
[x] behaviours implementing an explicit additional elastic-residual/Jacobian
    adapter contract (prototype target, not yet implemented)
```

This is a feasibility result, not a qualification result. No prototype
behaviour, J2 proof, SRIX proof or Méric proof has been run in this first gate.
